LTI 1.3 Handshake POC — how the demo works

A synthetic LTI platform completes a full OpenID Connect launch against a real ltijs tool hosted on Azure Container Apps. The tool validates the platform-signed token exactly as it would for a live LMS launch, then renders the authenticated student page.

Registering the tool — Dynamic Registration

Instead of an admin hand-copying a client_id, the LTI Dynamic Registration protocol has the tool and platform exchange configuration automatically. The included LMS simulator drives this end to end, minting the client_id before any launch.

Technically it is an OAuth 2.0 Dynamic Client Registration exchange bootstrapped by OpenID Connect discovery. The tool GETs the platform's openid-configuration to learn its authorize, token, JWKS, and registration endpoints, then POSTs its own client metadata (redirect URIs, JWKS URL, scopes, placements) to the registration endpoint, authenticated by the one-time registration_token. The platform replies with a generated client_id that both sides persist, so subsequent launches can be mutually verified.

Do it in the demo

  1. Open the LMS simulator Browse to the LMS URL (AZURE_LMS_URL). It shows “Not registered”.
  2. Click “Register tool (Dynamic Registration)” A popup opens the tool’s /register; the tool and LMS run steps A–C above. The status flips to Registered with a minted client_id, and the launch buttons enable.
  3. Launch Click “Launch as Student” or “Launch as Instructor” — this runs the launch handshake below and renders the authenticated page.

Headless equivalent: npm run test:dynreg drives registration and a student launch across both services and asserts the rendered page — no browser required.

The launch handshake

Technically the launch is an OpenID Connect implicit flow (response_type=id_token) begun by third-party-initiated login. Step 1 hands the platform-initiated click to the tool; Step 2 lets the tool mint its own nonce and state before any token exists, which makes the token replay-proof and binds the result to this browser; Step 3 delivers the platform-signed id_token, which the tool verifies against the platform's JWKS; Step 4 renders only once every claim checks out. The hops are browser redirects, not server-to-server calls, so the platform can attach the user's session and the tool can set and re-read its state cookie.

Reading the handshake, step by step

  • 1
    Platform → Tool · unauthenticated Login initiation The LMS pokes the tool at /login to say “a launch is coming.” It carries identifiers only (iss, client_id, deployment_id, login_hint, target_link_uri). The tool trusts nothing yet — it just uses iss+client_id to find which platform this is.
  • 2
    Tool → Platform · sets up security Authentication request The tool mints a fresh state (anti-CSRF) and nonce (anti-replay), stores them (cookie + database), and redirects the browser to the platform’s authorize endpoint carrying them. This is how a platform-triggered launch becomes a tool-controlled OIDC request.
  • 3
    Platform → Tool · authenticated Authentication response (the launch) The platform POSTs an id_token — a JWT signed with its private key — plus the state. The tool verifies the signature with the platform’s public key and checks iss, aud, exp, nonce, deployment_id, and that state matches its cookie.
  • 4
    Tool → Browser Resource display Every check passes, so the tool reads the token’s claims (user, roles, course context) and renders the authenticated page.

Every field, and why it’s there

The parameters do three jobs: establish identity (who is talking, to whom, about what), provide security correlation, and carry the payload (who the user is).

Identity & routing — who / to whom / about what
issIssuer. Identifies the platform (the LMS). The tool keys its registration lookup on this to find the platform’s public key and endpoints. A real LMS uses a fixed issuer URL; ours is a placeholder.
client_idThe tool’s registration ID at the platform. It reappears as the token’s aud, so a token can prove it was minted for this tool and no other.
deployment_idWhich deployment of the tool under that client_id — one registration can be deployed to many courses or accounts.
login_hintOpaque handle the platform uses to remember the user/session. The tool echoes it back untouched in Step 2 and never decodes it.
target_link_uriWhere the tool should ultimately land the user (the final resource). Verified at launch and used for the Step 4 destination.
redirect_uriIn Step 2 the tool tells the platform where to send the token; it must exactly match a value registered on the platform (prevents token delivery to an attacker).
Security correlation
stateAnti-CSRF. A random value the tool creates in Step 2 and stores in a cookie. The platform echoes it back with the token; the tool checks they match to prove the response belongs to the same browser that started the launch.
nonceAnti-replay. A random single-use value the tool creates in Step 2. It must appear inside the signed id_token; the tool checks it matches and hasn’t been seen before, so an old token can’t be reused.
the cookieCarries state in the browser between Step 2 and Step 3. This is the value that must survive the round-trip — and the one that breaks in LMS iframes (third-party cookie blocking).
The id_token — the signed payload
id_tokenThe signed JWT itself — the only authenticated message. Signed by the platform’s private key, verified with its public key.
alg / kidJWT header: RS256 and the key id, telling the tool which public key verifies the signature.
audAudience — equals the tool’s client_id. Rejects a token minted for a different tool.
exp / iatExpiry and issued-at timestamps — bound the token’s lifetime so it can’t be used indefinitely.
subThe user’s stable identifier at the platform. Always present, even when name/email are withheld.
name / emailUser profile fields, released according to the platform’s privacy level.
rolesThe user’s role URIs (e.g. …membership#Learner). Drives what the tool shows — the whole student vs. instructor distinction lives here.
contextThe course: id, label, title, type. Scopes the launch to a specific course.
message_type
version		LtiResourceLinkRequest and 1.3.0 — declare this is a standard LTI 1.3 resource-link launch.
resource_linkIdentifies the specific link/placement that was clicked inside the course.

How authentication works

Traffic goes both ways, but the cryptographic authentication is one-directional and uses asymmetric keys — no shared secret.

PROVES IDENTITY

Platform → Tool. The platform signs the id_token with its private key; the tool verifies with the matching public key (a real LMS publishes it at a JWKS URL; our POC registers a static key). A valid signature proves the sender holds the platform’s private key.

NOT CREDENTIALS

state and nonce don’t authenticate anyone — they’re anti-CSRF and anti-replay glue. iss, client_id, login_hint are identifiers, not secrets.

REVERSE DIRECTION

The tool only authenticates back to the platform for optional LTI Advantage services (grades, roster), using its own signing key via OAuth 2.0 client-credentials. Not part of this handshake — which is why the tool’s /keys is dormant here.

TRANSPORT

Every hop is HTTPS, so TLS server certificates authenticate the domains (the browser confirms it’s really the tool, really the LMS). That’s separate from the LTI-level JWT authentication above.

Run the demo

Run everything locally with one command — MongoDB (Docker) plus the tool and LMS simulator on localhost:

npm install
npm run local        # tool :3000, LMS :4000, Mongo :27017

Then open the LMS at http://localhost:4000 and follow the steps below. On Azure it is identical — open azd env get-value AZURE_LMS_URL instead. (Local runs the tool in dev mode so the browser launch works over plain http.)

  1. Open the LMS simulator The LMS admin Developer Keys page — http://localhost:4000 locally, or the Container App URL (azd env get-value AZURE_LMS_URL) on Azure. It shows no LTI keys yet.
  2. Register the tool (Dynamic Registration) Click “+ LTI Registration (Dynamic)”, leave the tool’s registration URL, and click Register. A popup opens the tool’s Install screen (name, target link, scopes); click Register there. The popup closes and a key card appears with the minted client_id and deployment.
  3. Launch Click Launch as Student or Launch as Instructor. A real OIDC launch runs (login → authorize → signed id_token) and the tool opens as an AI study-assistant chat that greets the user and shows the LTI context (course, role, deployment).
  4. Headless proofs (CI-able) Prove the same flows without a browser: 
    npm test          # static-platform handshake
npm run test:dynreg   # Dynamic Registration + launch, end to end
    Expect PASS from each. npm run demo also runs a single-service launch in a real headed browser.
  5. Show the persisted state Locally, connect to mongodb://localhost:27017/ltijs (published by npm run local); on Azure, open the lti-demo Cosmos account → Data Explorer → the ltijs database. Either way you see the platform registration (including the dynamically registered one) and the launch nonce/state records.

Re-run Dynamic Registration anytime with the LMS Forget registration button or npm run reset. The tool accepts a launch only because the token’s signature, issuer, audience, one-time nonce, expiry, and deployment all validate — break any one and it’s rejected. Switching student ↔ instructor is a launch choice only; the tool renders whatever role the token asserts.
